# 一、项目解决什么问题

## 1.1 直觉版本

设施农业数字孪生需要把自然语言业务需求——比如"构建 eggplant 温室资产方案：3 株重点植株采用 high_fidelity，13 株背景植株采用 lightweight_glb"——变成精确的、可执行的场景模型（typed object graph）。这涉及对象创建、层级挂载、属性配置、数据绑定、单位转换、资产路由、关系建立——每一步都必须符合农业领域知识规则。

**核心困难**：直接让 LLM Agent 做这件事，它会在多个环节违反领域约束——创建不存在的对象类型、把传感器挂到错误层级、绑定数据时搞错单位、修复错误时引入更严重的违规。这些不是"性能差"，而是**安全性问题**：Fatal Violation 意味着场景模型根本不可用。

## 1.2 Scientific Problem

**Problem**：现有 LLM Agent 在构建设施农业数字孪生场景时，无法可靠地满足领域知识约束。直接让 LLM 操作场景结构，场景有效性（CVSR）仅 0.48，且产生 25% 的致命违规（Fatal Violation Rate）。

**Key Insight**：LLM 擅长理解自然语言意图（semantic understanding），但不擅长保证结构化约束满足（constraint satisfaction）。正确的设计不是让 LLM 做更多，而是把 LLM 的角色限制在它擅长的事情上——理解意图和做出有界语义决策——而把所有涉及结构确定性的工作交给确定性代码。

## 1.3 Central Thesis

> KAFarmTwin does not ask an LLM to directly author a structured agricultural digital-twin scene. Instead, the LLM expresses compact semantic intent through an intermediate representation (IntentIR) and makes bounded repair decisions from a typed action space, while agricultural ontology, policies, and mappings are compiled into executable structure and enforced through validation and deterministic execution.

## 1.4 它不是在解决什么问题

- **不是** "哪个 LLM 更强"——五个模型都能被 KAFarmTwin 提升
- **不是** 通用场景构建——限定在设施农业数字孪生的五类任务（rule_repair, data_binding, memory_query, scene_construction, asset_routing）
- **不是** agent benchmarking——比的是约束满足能力，不是推理能力
- **不是** multi-agent 协作——核心方法是单 agent + 结构化约束

# 二、真实系统架构：Task-Conditioned Knowledge-Constrained Architecture

## 2.1 核心设计原则

KAFarmTwin 共享约束组件（validator、typed repair、knowledge modules），但不同任务类型调用架构的不同子集。这不是一条统一线性 pipeline，而是一个 **task-conditioned hybrid architecture**。

## 2.2 架构流程

```
User Natural-Language Request
        ↓
Task/Request Interpretation (task_type routing)
        ↓
Task-Conditioned Routing
        │
        ├── Asset Routing / Scene Construction Path
        │       ↓
        │   [1 LLM call] emit_intent → IntentIR
        │       ↓
        │   [Deterministic] expand_graph → typed object graph
        │       ↓
        │   [Deterministic] bind_scene + compile_asset_routes
        │       (ontology, binding_vocab, asset_policy, unit_registry)
        │
        ├── Data Binding Path
        │       ↓
        │   [Deterministic] seed_nodes_from_initial_state
        │   (preserves existing object graph, no LLM rebuild)
        │       ↓
        │   [1 LLM call] LLM emits bindings only
        │       ↓
        │   [Deterministic] timestamp contract enforcement
        │
        ├── Rule Repair Path
        │       ↓
        │   [Deterministic] seed from broken initial_state
        │   (no LLM calls for scene construction)
        │
        └── Memory Query Path
                ↓
            [Deterministic] build_memory_answer
            (0 LLM calls, pure retrieval + aggregation)
        
        ↓ (all paths converge)

Shared Constrained Stage
        ↓
    [Deterministic] ValidatorAPI.validate (rule engine R1–R7)
        ↓ (if violations exist)
    Typed Conflict Classification + Priority Routing
        ↓
    Candidate Actions (from typed_deterministic.candidate_actions_for)
        ↓
    [LLM call] Bounded Decision: LLM selects ONE action from candidates
        ↓
    [Deterministic where applicable] typed_deterministic.apply_action
    (mechanical patch instantiation; LLM full patch only for ambiguous cases)
        ↓
    Transactional Apply + Local Revalidate
    (deep-copy → apply → check for new fatals → rollback if needed)
        ↓
    [Loop: up to 3 repair rounds]
        ↓
    [Deterministic] Final emission: scene.plan → layout.solve → layout.validate
        ↓
    [Deterministic] Canonicalize output
        ↓
    Final Digital Twin Scene
```

## 2.3 各路径使用哪些模块

| 路径 | IntentIR | Compiler | Ontology | Stepwise Builder | Repair Loop | Memory |
|---|---|---|---|---|---|---|
| Asset Routing | ✅ | ✅ expand_graph + bind_scene | ✅ | ❌ | ✅ | ❌ |
| Scene Construction | ❌ (用 stepwise) | ❌ | ❌ | ✅ (3 LLM calls) | ✅ | ❌ |
| Data Binding | ❌ | ❌ | ❌ | ✅ bindings_only (1 LLM) | ✅ | ❌ |
| Rule Repair | ❌ | ❌ | ❌ | ❌ (seeds from initial_state) | ✅ | ❌ |
| Memory Query | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ (0 LLM) |

## 2.4 LLM 参与位置

- **emit_intent**（1 call）：从自然语言提取 IntentIR（scene_type, crop, groups, devices, missing_devices）
- **stepwise objects/relations/bindings**（3 calls）：scene_construction 任务中 LLM 生成完整对象图
- **bindings_only**（1 call）：data_binding 任务中 LLM 只生成绑定
- **typed repair decision**（1 call/round）：LLM 从候选修复算子中选择一个
- **typed repair full patch**（0–1 call/round）：仅在无法机械映射的 ambiguous 情况下，LLM 生成完整 patch

## 2.5 Deterministic 参与位置

- Knowledge Compiler（expand_graph, bind_scene, compile_asset_routes）
- Ontology lookup（类型、层级、属性、binding schema、关系约束）
- Validator（rule engine R1–R7）
- Typed conflict classification + priority routing
- Deterministic patch instantiation（typed_deterministic.apply_action）
- Transactional apply + local revalidate
- Layout solve + validate
- Canonicalize output
- Memory retrieval + aggregation
- Replay verification

## 2.6 Knowledge Constraint 生效位置

| 约束类型 | 在哪里生效 | 由谁执行 |
|---|---|---|
| 对象类型约束 | expand_graph / ontology lookup | Deterministic |
| 层级约束 | expand_graph / validator R1 | Deterministic |
| 属性约束 | expand_graph / validator R5 | Deterministic |
| Binding schema | bind_scene / validator R6 | Deterministic |
| 单位映射 | unit_registry / bind_scene | Deterministic |
| 资产路由 | compile_asset_routes / asset_policy | Deterministic |
| 规则表 | Knowledge Compiler → repair candidate actions | Deterministic |

# 三、IntentIR：紧凑语义中间表示

## 3.1 IntentIR 不是任务分类器

IntentIR 是从自然语言中提取出的 **compact semantic intermediate representation**——一个包含场景语义意图的结构化对象，而不是简单的 task_type 标签。

## 3.2 IntentIR 的真实字段（代码确认）

```python
@dataclass
class IntentIR:
    scene_type: str = "greenhouse"      # 场景类型
    crop: str = ""                      # 作物类型（如 "eggplant", "kale"）
    groups: list[dict] = []             # 对象组列表
    devices: list[dict] = []            # 设备行列表
    missing_devices: list[dict] = []    # 缺失设备占位
```

每个 group 包含：
- `object_type`：对象类型（如 "Plant", "CropRow"）
- `role`：角色（"entity", "focus", "background"）
- `count`：数量
- `asset_policy`（可选）：资产策略（"high_fidelity", "lightweight_glb"）
- `key_attrs`（可选）：关键属性
- `parent`（可选）：父节点提示

## 3.3 为什么 IntentIR 是关键技术设计

```
Natural Language
    → [LLM: 1 call] compact IntentIR（少量 groups + devices）
    → [Deterministic] Knowledge Compiler 展开为完整场景
    → Typed Object Graph
```

**核心优势**：LLM 只需输出一个紧凑的意图描述（远低于 ~1200 token 输出上限），不需要生成完整的对象实例、层级关系和全部 ID。这解决了 stepwise_builder 中输出截断的根本问题（F-018 root cause）。

**与 SingleAgent 的区别**：SingleAgent 让 LLM 通过 3 步分别生成 objects、relations、bindings（每步都有输出截断风险）。KAFarmTwin 的 IntentIR 路径只需 1 步 LLM 调用，其余由确定性编译器完成。

# 四、Knowledge Sources 与 Compiler 的关系

## 4.1 知识源 ≠ 编译器 ≠ 执行器

```
Knowledge Source          → Compilation            → Executable Constraint     → Runtime Enforcement
(ontology, policies,      (semantic_compiler.py)   (TypedObjectGraph,          (ValidatorAPI,
 unit_registry, etc.)                              candidate_actions)          typed_deterministic)
```

## 4.2 六个 Knowledge Module（代码确认）

| Module | 文件 | 内容 | 类型 |
|---|---|---|---|
| **Ontology** | `knowledge/ontology.py` | IDENTITY_TYPES（Camera/Sensor/Pump/Valve 等必须单独 emit 的类型）、ROOT_ID、HIERARCHY_WITHOUT_PARENT | 数据 + 常量 |
| **Constraint** | `knowledge/constraint.py` | DEVICE_DEFAULT_TARGET_CLASS、DEVICE_DEFAULT_METRIC、DEVICE_ASSET_CLASSES、AGGREGATABLE_TYPES | 数据 + 映射 |
| **Mapping** | `knowledge/mapping.py` | is_identity_type、is_aggregatable、resolve_parent_hint、find_child、find_contained_plant | 纯函数 |
| **Binding Vocab** | `knowledge/binding_vocab.py` | make_sensor_bind、make_asset_bind、canonical_metric、canonical_metrics | 构造函数 |
| **Asset Policy** | `knowledge/asset_policy.py` | ASSET_BY_TYPE（Pump→irrigation 等）、CROP_POLICY、asset_key_for、policy_for | 数据 + 函数 |
| **Unit Registry** | `knowledge/unit_registry.py` | unit_for_metric（temperature→celsius 等）、_UNIT_CANONICAL 标准化 | 数据 + 函数 |

**所有六个模块都是纯 deterministic 代码，零 LLM 调用。**

## 4.3 Compiler 如何消费 Knowledge Sources

`semantic_compiler.py` 导入所有六个 knowledge module：

```python
from knowledge.unit_registry import unit_for_metric
from knowledge.binding_vocab import make_sensor_bind, make_asset_bind
from knowledge.asset_policy import ASSET_BY_TYPE, asset_key_for, policy_for
from knowledge.ontology import IDENTITY_TYPES, ROOT_ID
from knowledge.constraint import DEVICE_DEFAULT_TARGET_CLASS, ...
from knowledge.mapping import is_identity_type, resolve_parent_hint, ...
```

Compiler 的三步操作：
1. **expand_graph**：使用 ontology + mapping + constraint 展开对象图（Greenhouse→CropRow→Plant 层级，设备挂载，ID 分配）
2. **bind_scene**：使用 binding_vocab + unit_registry + asset_policy 生成绑定（sensor_bind, asset binding, 单位标准化）
3. **compile_asset_routes**：使用 asset_policy 路由资产（focus→high_fidelity, background→lightweight）

# 五、Typed Repair 与 Bounded LLM Autonomy

## 5.1 普通 LLM Repair vs KAFarmTwin Typed Repair

**普通方式**：
```
验证失败 → LLM 看到错误信息 → LLM 自己决定怎么修 → 直接修改场景
```
问题：LLM 的修复可能引入新的 Fatal Violation。

**KAFarmTwin**：
```
验证失败 → 编译器分类冲突 + 生成候选修复算子集合
→ LLM 从集合中选择一个算子
→ 确定性代码执行修复（如果 action 可机械映射）
→ 事务性 apply + 本地重验证
```

## 5.2 Bounded LLM Autonomy

这是论文的核心设计思想，不是"LLM 从不修改场景"。

**真实行为**（代码确认）：

- **大多数机械可解析的 repair action**：LLM selects action → `typed_deterministic.apply_action()` 机械实例化具体 patch
- **Ambiguous / unmapped cases**：当 action 是 `ask_user` 或无法机械映射时，LLM 生成完整 patch（1 次额外 LLM 调用）

```python
# typed_deterministic.py
def candidate_actions_for(rule_id: str) -> list[str]:
    """返回该规则对应的候选修复动作"""
    # R4 → ["replace_asset", "create_placeholder", "ask_user"]
    # R1 → ["attach_to_root"]
    # R5 → ["fill_observes"]
    # ...

def apply_action(action, rule_id, violation, nodes, edges, bindings):
    """将 LLM 选择的 action 实例化为具体 patch"""
    if action == "replace_asset": ...   # 确定性
    if action == "attach_to_root": ...  # 确定性
    if action == "fill_observes": ...   # 确定性
    if action == "ask_user": return None  # LLM 需要自行生成 patch
```

## 5.3 为什么 bounded autonomy 比两个极端都更合理

| 方案 | 问题 |
|---|---|
| 完全自由 LLM repair | 可能引入新的 Fatal Violation（实验：Fatal 0→0.22） |
| 完全不用 LLM | 无法理解"哪种修复语义上合适" |
| **Bounded autonomy** | LLM 做语义决策（"用 replace_asset 还是 create_placeholder？"），确定性代码做机械执行 |

## 5.4 Typed Conflict 分类优先级

当 validator 发现多个 violation 时，按 `CONFLICT_PRIORITY` 排序：

```python
CONFLICT_PRIORITY = ["R4", "R2", "R1", "R3", "R5", "R6", "R7", "R8", "R9", "R10"]
```

Fatal 优先处理。每轮修复处理一个冲突。

## 5.5 事务性安全保障

```python
# 伪代码
state_before = deep_copy(current_state)
patch = apply_action(selected_action, ...)
apply_patch(patch)
if introduces_new_fatal_violations(current_state):
    rollback(state_before)  # 回滚
    break  # 退出修复循环
```

# 六、Validator 与 Replay

## 6.1 Validator

- **代码**：`validator_api.py` → 包装 `rule_engine.RuleEngine`
- **规则**：R1–R7（fatal + warning 两级）
- **关键**：方法和 evaluator 使用**同一个** ValidatorAPI 实例，防止方法博弈不同 validator

## 6.2 Replay

- **是什么**：把场景构建的操作序列从头重放，验证确定性和可重现性
- **为什么重要**：不可重放的场景依赖 LLM 的隐含状态，在生产环境中不可靠
- **数据**：KF Replay 0.808 vs SA 0.455

# 七、Baseline 详解

## 7.1 SingleAgent-AllTools（主 baseline）

| 维度 | 说明 |
|---|---|
| 工作方式 | 一个 LLM agent 拥有全部 13 个工具，直接根据用户请求操作场景 |
| 工具集 | ✅ 与 KAFarmTwin 完全相同 |
| ONTOLOGY_NOTE | ✅ **同样接收**（通过 llm.py 的 make_llm_call_fn 注入 system prompt） |
| Knowledge Compiler | ❌ 没有 |
| Typed Repair | ❌ 没有 |
| Deterministic Executor | ❌ 没有 |
| 与 KAFarmTwin 区别 | prompt 层面有 ontology 信息，但缺少**可执行的 ontology 强制执行**和 knowledge compilation |

**为什么是"最强公平 baseline"**：它代表"一个足够强的 LLM + 完整工具集 + prompt 层面知识"的上限。拥有与 KAFarmTwin 完全相同的工具和 ontology 提示，只是缺少编译器和类型化修复。如果 KAFarmTwin 连这个 baseline 都赢不了，说明 knowledge compilation 层没有价值。

**实验设计公平性**：
1. **同任务配对**：每个 300 个任务上，KF 和 SA 各跑一次
2. **同工具集**：13 个 deterministic 工具完全相同
3. **同 ontology 提示**：两者都通过 ONTOLOGY_NOTE 获得 ontology 信息
4. **同评估器**：同一个 ValidatorAPI + evaluator
5. **同 LLM**：都使用 DeepSeek-V4-Flash（多模型实验中各自模型）
6. **统计检验**：McNemar 配对检验 + 10,000 bootstrap CI

## 7.2 ReAct-AllTools

- 经典 Think→Act→Observe 循环，无知识约束
- 结果：CVSR = **0.000**（test_v2 上 20 个任务全部失败）

## 7.3 GenericMultiAgent-AllTools

- 多 agent 分工（Planner/Layout/Asset/Binding/Validator），但无领域知识
- 结果：CVSR = **0.010**

## 7.4 GenericRepair-AllTools

- 有修复步骤，但修复是通用的（LLM 直接修改场景）
- 结果：CVSR = **0.060**

## 7.5 为什么 External300 只保留 SA

1. **规模约束**：4 个 baseline × 300 任务 = 1200 次额外调用，成本不现实
2. **信息饱和**：test_v2 已证明 ReAct/GenericMulti/GenericRepair 全部崩溃（< 0.06）
3. **SA 是最强公平 comparator**：拥有完整工具集 + ontology 提示的单 agent
4. **统计功效**：300 任务配对比较已足够检测 Δ = 0.24 的效应

# 九、消融实验（20 tasks × 5 repeats = 100 runs per variant, 4 variants = 400 total runs）

## 9.1 结果

| 变体 | CVSR | Fatal | Binding F1 | Object F1 |
|---|---:|---:|---:|---:|
| **full** | 0.550 | 0.000 | 0.529 | 0.796 |
| A1_no_compiler | **0.370** | 0.010 | 0.329 | 0.721 |
| A2_no_typed_repair | **0.580** | **0.220** | 0.329 | 0.798 |
| A3_no_ontology | 0.530 | 0.000 | **0.453** | 0.796 |

## 9.2 A1（去掉 Knowledge Compiler）

- **去掉了什么**：`KAFARMTWIN_ABLATE_COMPILER=1` → 回退到 stepwise_builder（与 SingleAgent 相同的 3 步 LLM 调用）
- **为什么资产构建明显下降**：没有编译器的 expand_graph，LLM 必须自行生成完整的层级、ID 和资产路由——这正是 F-018 root cause（输出截断）的来源
- **消融证据**：asset_routing CVSR 0.95→0.00, 整体 CVSR -18pp
- **证明了什么**：Knowledge Compiler 是构建能力的决定性来源

## 9.3 A2（去掉 Typed Repair）

- **去掉了什么**：`KAFARMTWIN_ABLATE_REPAIR=1` → 跳过整个 repair loop
- **为什么 CVSR 反而上升（0.550→0.580）**：去掉 repair 后，LLM 的 scene construction 偶尔"碰巧"直接生成了合法场景，不需要修复。但代价是 Fatal Rate 从 0 飙升到 0.22
- **Fatal-state paired flips 22:0**：在 100 次运行中，有 22 个 paired runs 中 A2 产生了 fatal violation 而 full 保持 clean，反向为 0。这证明 typed repair 的贡献是**单向安全性保障**
- **证明了什么**：Typed Repair 的核心贡献是安全性和可靠性，而非平均 CVSR

## 9.4 A3（去掉 Ontology）

- **去掉了什么**：`KAFARMTWIN_ABLATE_ONTOLOGY=1` → 禁用 deterministic executor，LLM 生成完整 patch
- **为什么主要影响 Binding F1**：ontology 约束主要控制"对象之间的关系是否正确"——传感器挂载到正确的温室、数据绑定到正确的控制器
- **消融证据**：Bind-F1 0.529→0.453, CVSR 变化小（0.550→0.530）
- **证明了什么**：Ontology 约束主要贡献于语义/绑定正确性

## 9.5 三组件贡献总结

```

                      证据：A1 CVSR -18pp, asset CVSR 0.95→0.00

Typed Repair        → 安全性 (Safety)
                      证据：A2 Fatal 0→0.22, paired flips 22:0

Ontology            → 语义/绑定正确性 (Semantic Correctness)
```

# 十三、Worked Example：EXT-AR-001（Asset Routing）

## Step 1. Original User Request

**Task ID**: EXT-AR-001
**Dataset**: External300
**Task type**: asset_routing

**Prompt**:
> 构建 eggplant 温室资产方案：3 株重点植株采用 high_fidelity，13 株背景植株采用 lightweight_glb。

**initial_state**: {}（空，需要从零构建）

## Step 2. IntentIR（1 LLM call）

LLM 提取 compact semantic intent：

```json
{
  "scene_type": "greenhouse",
  "crop": "eggplant",
  "groups": [
    {"object_type": "Plant", "role": "focus", "count": 3,
     "key_attrs": {"asset_policy": "high_fidelity"}},
    {"object_type": "Plant", "role": "background", "count": 13,
     "key_attrs": {"asset_policy": "lightweight_glb"}}
  ],
  "devices": [],
  "missing_devices": []
}
```

**LLM 决定了什么**：场景类型、作物、对象组及数量、角色和资产策略。
**LLM 没有决定什么**：对象 ID、层级结构、父节点分配、资产绑定——这些由编译器完成。

## Step 3. Knowledge Compilation（Deterministic）

**expand_graph** 使用 ontology + mapping + constraint：

1. 创建 root：`Greenhouse`（ROOT_ID = "greenhouse_1"）
2. 创建 `CropRow` 作为 Greenhouse 的子节点
3. 将 3 个 focus Plant 和 13 个 background Plant 挂载到 CropRow
4. 分配唯一 ID（`greenhouse_1`, `croprow_1`, `eggplant_focus`, `eggplant_background`）

**bind_scene** 使用 binding_vocab + asset_policy + unit_registry：

```json
{
  "bindings": [
    {"subject": "eggplant_focus", "target": "eggplant_focus_asset",
     "type": "asset",
     "metadata": {"asset_key": "eggplant_focus", "policy": "high_fidelity"}},
    {"subject": "eggplant_background", "target": "eggplant_background_asset",
     "type": "asset",
     "metadata": {"asset_key": "eggplant_bg", "policy": "lightweight_glb"}}
  ]
}
```

**compile_asset_routes**：focus→high_fidelity, background→lightweight_glb（由 asset_policy 确定性路由）

## Step 4. Validation

Validator（rule engine R1–R7）检查：
- R1：层级完整性 ✅
- R2：绑定有效性 ✅
- R3：空间约束 ✅
- R4：资产类型匹配 ✅
- R5：设备配置完整性 ✅
- R6：数据绑定完整性 ✅
- R7：证据完整性 ✅

该任务直接通过验证，无需 repair。

## Step 5–7. 不适用（无 repair）

## Step 8. Final Validated State

- **Objects**: Greenhouse → CropRow → 3 focus Plants + 13 background Plants
- **Relations**: contains edges (Greenhouse→CropRow→Plants)
- **Bindings**: focus→high_fidelity, background→lightweight_glb
- **Fatal violations**: 0
- **Replay**: ✅

**Gold 标准匹配**：required_nodes、required_edges、required_bindings 全部满足。

# 十四、Worked Example：EXT-RR-001（Rule Repair）

## Step 1. Original User Request

**Task ID**: EXT-RR-001
**Task type**: rule_repair

**Prompt**:
> 修复既有场景中的资产类型错误：ERR001_pump 是 Pump，却绑定了 corn 植物资产。仅将其 asset_key 修正为 irrigation。

**initial_state**: 包含一个 broken scene——ERR001_pump 的 asset_key 是 "corn"（错误），应为 "irrigation"。

## Step 2. Task Routing

检测到 rule_repair → 从 initial_state 直接 seeding（不经过 IntentIR 或 compiler）。

## Step 3. Seeding（Deterministic）

从 initial_state 提取已有对象图：
- ERR001_greenhouse (Greenhouse)
- ERR001_row (CropRow, parent: greenhouse)
- ERR001_pump (Pump, parent: greenhouse, asset_key: "corn" ← 错误)

## Step 4. Validation

Validator 检测到 **R4 violation（fatal）**：ERR001_pump 的 asset_key "corn" 不匹配 Pump 的合法 asset 类（应为 "irrigation"）。

## Step 5. Typed Repair

**Typed conflict classification**：
- rule_id: R4
- severity: fatal
- object: ERR001_pump
- observed: asset_key = "corn"
- expected: asset_key = "irrigation"

**Candidate actions**（from `typed_deterministic.candidate_actions_for("R4")`）：
- `replace_asset`（机械可解析）
- `create_placeholder`
- `ask_user`

**Bounded LLM Decision**：LLM 选择 `replace_asset`（最合适的语义选择）。

## Step 6. Deterministic Instantiation

`typed_deterministic.apply_action("replace_asset", "R4", ...)` 机械生成 patch：

```json
{"patch_op": "replace",
 "target": "ERR001_pump",
 "changes": {"asset_key": "irrigation"},
 "binding": {"subject": "ERR001_pump", "target": "ERR001_pump",
             "type": "asset", "metadata": {"asset_key": "irrigation", "fixed": true}}}
```

## Step 7. Transactional Apply + Revalidate

- deep-copy state before patching
- apply patch
- local revalidate：不再有 R4 violation
- no new fatals introduced → patch accepted

## Step 8. Final State

- ERR001_pump.asset_key = "irrigation" ✅
- Fatal violations: 0
- Critical object ERR001_pump 已被实际修改 ✅

**KAFarmTwin 不同**：问题不是 LLM agricultural QA 或 crop decision making，而是 **LLM-guided constrained digital-twin scene construction**。

**典型工作**：LLM for DT interaction, LLM for DT update, LLM for knowledge graph, LLM for simulation/control, LLM-driven tool use。

**通常模式**：natural language → LLM → command / KG update / DT control

**KAFarmTwin 模式**：natural-language intent → compact IntentIR → domain compilation → typed agricultural object graph → constrained validation and repair

# 十六、技术贡献

## Contribution 1: Intent-to-Graph Knowledge Compilation

LLM 输出 compact IntentIR，domain knowledge compiler 展开为 typed object instances、hierarchy、relations、bindings、asset routes。这是 semantic intent → executable structure 的关键桥梁。

**与普通 Agent 的本质区别**：普通 Agent 让 LLM 直接生成完整对象图（输出截断风险 + 约束违反）；KAFarmTwin 让 LLM 只表达意图，编译器负责结构化。

**实验证明**：A1 去掉编译器 → asset CVSR 0.95→0.00, CVSR -18pp。

## Contribution 2: Typed Repair with Bounded LLM Autonomy

validator → typed conflict → candidate action set。LLM 负责 semantic choice，deterministic code 负责 mechanically resolvable instantiation。

**与普通 self-repair 的本质区别**：普通 self-repair 让 LLM 自由修改场景（可能引入新 Fatal）；KAFarmTwin 限制为有界候选算子。

**实验证明**：A2 去掉 typed repair → Fatal 0→0.22, paired flips 22:0; 五模型 KF Fatal ≈0 vs SA 0.23–0.29。

## Contribution 3: Traceable Knowledge-Constrained Scene Execution

把 free-form LLM decision 和 structured scene mutation 分离。通过 validation、evidence recording、replay、constrained execution 提高 scene state 的 traceability / reproducibility / safety。

**实验证明**：KF Replay 0.808 vs SA 0.455; Evidence Precision 1.000 vs 0.947。

## Evaluation Contribution（不是方法创新）

- External300 paired controlled benchmark（300 tasks, McNemar p<10⁻¹⁶）
- Component ablation（20 tasks × 5 repeats × 4 variants）
- Multi-baseline test_v2（5 paradigms）
- Five-model-family validation（MODEL_GENERALIZATION_PASS）
- Fatal / Replay / CVSR / Binding 等 safety metrics

# 二十四、最终项目总结

1. **我们做了一个什么东西？** 一个 knowledge-constrained framework，让 LLM 在确定性约束内构建设施农业数字孪生场景。

2. **Baseline 到底是什么？** SingleAgent-AllTools：拥有完整工具集 + ontology prompt 但缺少 knowledge compilation 和 typed repair 的 LLM Agent。

3. **我们和 baseline 最本质的区别？** LLM 的角色不同：Baseline 中 LLM 做所有事；KAFarmTwin 中 LLM 只做 IntentIR 提取和 bounded repair decisions，约束满足由确定性代码完成。

4. **真正的技术创新？** 三个：IntentIR → Knowledge Compiler（知识→约束）、Typed Repair with Bounded Autonomy（有界修复）、Traceable Constrained Execution（可追踪执行）。

5. **性能提升主要体现在？** 安全性（Fatal 0.25→0.00）、可靠性（Replay 0.46→0.81）、绑定正确性（Binding F1 0.20→0.59）。

6. **哪个实验最有说服力？** External300 主实验：300 任务、配对比较、McNemar p<10⁻¹⁶、bootstrap CI [0.18, 0.29]。

7. **哪个消融最能证明机制？** A2（去掉 typed repair）：Fatal 0→0.22, paired flips 22:0。

8. **一句话向编辑介绍？**

> "KAFarmTwin reduces fatal violations from 25% to 0% and improves scene validity by 23.7 percentage points in farm digital-twin construction by confining the LLM to compact intent expression and bounded repair decisions, while agricultural knowledge is compiled into executable structure and enforced through deterministic validation and execution."
