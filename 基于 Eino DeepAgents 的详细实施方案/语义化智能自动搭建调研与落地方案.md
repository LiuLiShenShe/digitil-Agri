# 数字孪生平台语义化智能自动搭建调研与落地方案

## 1. 结论

老师希望的能力可以定义为“语义化智能自动搭建”：用户用自然语言描述目标场景，例如“帮我搭一个智慧农业园区，左侧是三块玉米地，右侧三个温室，中间放气象站和灌溉设备”，平台自动在网页 3D 编辑器中生成可预览、可编辑、可保存的场景。

这可以做成智能体，但第一版不建议做成完全自主智能体。更稳妥的定义是“受控场景搭建智能体”：LLM 负责理解意图和生成结构化场景方案，后端/前端工具负责资产检索、布局约束、模型加载、碰撞校验和场景保存。LLM 不直接改数据库，而是输出 JSON 计划，由白名单工具执行。

结合当前平台现状，最佳路线不是端到端训练一个“文本生成 3D 场景大模型”，而是采用模块化流程：

```
自然语言需求
  -> LLM 语义解析
  -> 场景图 / 场景 JSON
  -> 资产检索或 TRELLIS.2 生成缺失 GLB
  -> 布局规则与约束求解
  -> Three.js 网页端加载模型
  -> 用户确认、微调、保存场景
```

这样最贴合当前项目：你们已有 `loadModel(url, options)`、`applyTemplate()`、`saveScene()`，后端场景保存也只需要模型的 `url / scale / offset / angle`。所以首版重点不是改渲染底座，而是新增“文本到场景 JSON”的智能规划层。

## 2. 相关文献和方法

### 2.1 Holodeck：语言引导生成 3D 交互环境

论文：Holodeck: Language Guided Generation of 3D Embodied AI Environments  
项目页：https://yueyang1996.github.io/holodeck/  
代码：https://github.com/allenai/Holodeck  
arXiv：https://arxiv.org/abs/2312.09067

核心思想：用户输入自然语言，系统用 GPT-4 推理场景应包含什么对象、对象之间有哪些空间关系，再从 Objaverse 资产库检索 3D 模型，通过优化布局满足空间约束，最终生成可交互 3D 环境。

对本项目的启发最大：不要让 LLM 直接“画 3D”，而是让 LLM 生成对象清单和空间关系，例如“温室 A 在道路右侧”“气象站位于地块中央”“摄像头靠近入口”。后续由程序转换成 Three.js 坐标。

适配程度：思路高度适配；代码直接复用难度中等偏高，因为 Holodeck 依赖 AI2-THOR/Unity 生态，不是 Three.js/GLB 场景编辑器。

### 2.2 LayoutGPT：LLM 作为布局规划器

论文：LayoutGPT: Compositional Visual Planning and Generation with Large Language Models  
项目页：https://layoutgpt.github.io/  
代码：https://github.com/weixi-feng/LayoutGPT  
arXiv：https://arxiv.org/abs/2305.15393

核心思想：让 LLM 输出类似样式表的布局描述，用于 2D 图像布局和 3D 室内场景布局。它证明了 LLM 可以处理数量关系、空间关系和部分场景补全。

对本项目的启发：很适合作为第一版技术路线。我们可以让 LLM 输出受控 JSON：

```json
{
  "sceneName": "智慧农业示范园区",
  "ground": { "width": 1200, "height": 1000, "color": "#7f8f55" },
  "objects": [
    { "type": "greenhouse", "count": 3, "layout": "column", "area": "east" },
    { "type": "corn", "count": 6, "layout": "grid", "area": "west" },
    { "type": "weather_station", "count": 1, "area": "center" }
  ],
  "relations": [
    { "subject": "weather_station", "predicate": "near", "object": "field_center" }
  ]
}
```

后端或前端再把这个 JSON 展开成当前项目能加载的模型数组。

适配程度：高。它本身不是完整生产系统，但方法非常适合作为你们的“文本到布局”模块。

### 2.3 CommonScenes：场景图到 3D 场景

论文：CommonScenes: Generating Commonsense 3D Indoor Scenes with Scene Graph Diffusion  
代码：https://github.com/ymxlzgy/commonscenes  
OpenReview：https://openreview.net/forum?id=1SF2tiopYJ  
arXiv：https://arxiv.org/abs/2305.16283

核心思想：输入场景图，节点表示对象，边表示对象之间的关系，然后用扩散模型生成合理的 3D 室内场景布局和几何形状。

对本项目的启发：场景图是语义化自动搭建的关键中间表示。可以把用户的话转成：

```
节点：温室、玉米地、道路、水塔、摄像头、传感器
边：温室-沿道路排列，摄像头-监控-入口，传感器-位于-温室内部
```

然后再转成场景对象坐标。

适配程度：研究价值高，直接工程复用难度高。它依赖 3D-FRONT/3D-FUTURE 等室内数据集和 GPU 训练/推理，且偏室内家具，不适合直接作为农业数字孪生 MVP。

### 2.4 ATISS / DiffuScene：室内场景自动合成

ATISS 项目页：https://research.nvidia.com/labs/toronto-ai/ATISS/  
ATISS 代码：https://github.com/nv-tlabs/ATISS  
DiffuScene 项目页：https://tangjiapeng.github.io/projects/DiffuScene/  
DiffuScene 代码：https://github.com/tangjiapeng/DiffuScene  

核心思想：根据房间类型、户型、已有对象等条件自动生成合理的室内家具布局。ATISS 用自回归 Transformer，DiffuScene 用扩散模型。

对本项目的启发：可以学习“场景补全”和“布局合理性”的思想，比如用户先手动放两个温室，再说“在旁边补齐灌溉系统和传感器”，系统自动补齐。

适配程度：中等。研究方向相关，但数据域偏室内，不如 LayoutGPT + 规则布局适合农业园区。

### 2.5 SceneCraft：布局引导的 3D 场景生成

项目页：https://orangesodahub.github.io/SceneCraft/  
代码：https://github.com/OrangeSodahub/SceneCraft  
arXiv：https://arxiv.org/abs/2410.09049

核心思想：用户提供文本和自由布局，系统生成符合布局的复杂 3D 场景。

对本项目的启发：证明“文本 + 布局先验”比单纯文本生成更可控。你们平台也应保留用户确认和编辑能力，不追求一次生成完美。

适配程度：研究参考价值高，但工程复杂度高，首版不建议直接接入。

### 3.1 各开源项目/方法在本系统中的作用

单个开源项目基本不能直接完成“说一句话，网页上自动搭好数字孪生场景”的完整要求。它们更适合作为不同模块的参考或组件：Eino DeepAgents 负责后端智能体编排，LayoutGPT/Holodeck 负责语义规划思想，TRELLIS.2 负责缺失 GLB 单体资产生成，当前平台负责 Three.js 渲染、模型加载和场景保存。

| 项目/方法 | 在本项目里的角色 | 能解决的问题 | 不能解决的问题 | 能否单独完成你的要求 |
|---|---|---|---|---|
| Eino / Eino DeepAgents | 后端智能体框架 | 组织主 Agent、子 Agent、工具调用、任务规划；适合接入 Go 后端 | 不自带农业场景知识、不自带 Three.js 布局器、不自带 GLB 模型库 | 不能单独完成，但最适合做核心编排层 |
| page-agent | 前端网页操作助手 | 让用户用自然语言点击按钮、填写表单、触发页面已有功能 | 不擅长 Three.js 画布里的空间布局、模型坐标、碰撞检测、拖拽摆放 | 不能单独完成，可做演示入口或辅助操作 |
| Holodeck | 架构参考 | 证明“语言 -> 对象清单 -> 空间关系 -> 资产检索 -> 布局优化”这条路线可行 | 依赖 AI2-THOR/Unity，不是你们的 Three.js/GLB 技术栈 | 不能直接完成，适合借鉴总体流程 |
| LayoutGPT | 文本转布局参考 | 让 LLM 把自然语言转成布局 JSON，处理数量、方位、空间关系 | 不负责资产生成、不负责业务绑定、不负责网页落地 | 不能单独完成，但很适合 MVP 的场景规划模块 |
| CommonScenes | 场景图生成研究参考 | 用场景图表达对象和关系，并生成更合理的 3D 场景 | 训练和数据依赖重，偏室内家具，不贴合农业园区 | 不适合直接完成，适合写论文相关工作 |
| ATISS / DiffuScene | 自动布局/场景补全参考 | 自动补全室内对象布局，提供“已有对象 -> 补齐场景”的思路 | 偏室内数据集，和农业数字孪生资产差异大 | 不能直接完成，适合后续高级布局参考 |
| SceneCraft | 文本 + 布局生成 3D 场景参考 | 证明加入布局约束后 3D 生成更可控 | 工程复杂，生成结果不一定是可编辑业务对象 | 不适合 MVP，适合作为远期方向 |
| TRELLIS.2 | 缺失资产生成模块 | 根据图片/提示生成单个 GLB 资产，补模型库短板 | 不负责完整场景规划、不知道对象该放在哪里 | 不能单独完成，但能补齐“没有模型”的问题 |
| 当前数字孪生平台 | 执行与呈现层 | 已有模型加载、场景模板、场景保存、模型入库、前端编辑能力 | 缺少自然语言理解、语义规划和自动布局 | 是落地基础，必须保留并扩展 |

### 3.2 是否能完成“说出来就自动搭建”的要求

可以完成，但需要组合实现，不能指望某一个开源项目直接替换当前平台。

推荐组合如下：

```text
Eino DeepAgents
  负责：后端智能体编排、工具调用、任务拆解、多轮修正

LayoutGPT / Holodeck 思路
  负责：把自然语言转成对象清单、空间关系、ScenePlan JSON

规则布局器
  负责：把“左边三块田、右边三个温室、中间一条路”转换成 offset / scale / angle

模型库语义索引
  负责：把“温室/大棚/玻璃房”匹配到 greenhouse.glb

TRELLIS.2
  负责：当模型库没有“农业欢迎牌/特殊设备”等资产时生成 GLB

当前 Three.js 平台
  负责：加载 GLB、预览、拖拽微调、保存场景
```

因此，你的目标可以拆成三种完成程度：

| 完成程度 | 用户体验 | 技术实现 | 推荐阶段 |
|---|---|---|---|
| MVP 可完成 | 用户说一句话，系统生成标准农业场景并放到网页上 | LLM 输出 ScenePlan，规则布局器生成坐标，调用现有 `scene.loadModel()` | 第一阶段 |
| 增强版可完成 | 用户说一句话，缺少的模型自动进入 GLB 生成任务，完成后可替换 | 在 MVP 基础上接 TRELLIS.2 资产任务流 | 第二阶段 |
| 智能体闭环可完成 | 系统能读当前场景、自动补全、发现冲突、修正布局、询问用户确认 | Eino DeepAgents + 多工具调用 + 布局校验 + 用户确认 | 第三阶段 |

第一阶段建议把目标收窄为“农业园区常见布局自动搭建”，不要一开始承诺任意复杂场景。比如下面这些需求第一版可以完成：

- “搭一个智慧农业示范园区，左边 6 块农田，右边 3 个温室，中间一条路，中央放气象站。”
- “创建一个标准温室场景，两个大棚，每个大棚里放传感器，旁边放灌溉设备。”
- “在当前场景里补齐摄像头、气象站、水塔和灌溉系统。”

下面这些需求第一版不建议承诺完全自动完成：

- “生成一个完全真实比例、符合工程图纸的园区。”
- “任意一句话生成任意风格、任意资产、完全可生产使用的数字孪生。”
- “自动理解 Three.js 画布里的所有已有模型并进行复杂物理避让。”

### 3.3 推荐选型结论

如果要写进课题方案，可以这样定：

1. 后端智能体框架优先考虑 Eino DeepAgents，因为项目后端是 Go，Eino 的工具调用、Agent 编排和多 Agent 模式更容易和现有服务融合。
2. 前端不依赖 page-agent 完成 3D 搭建。page-agent 可作为“网页自然语言操作助手”或演示增强，例如让用户说“打开模型库”“保存场景”，但核心搭建必须走结构化 `ScenePlan` 和 Three.js API。
3. 场景规划方法借鉴 LayoutGPT 与 Holodeck：让 LLM 输出对象、数量、方位、关系，而不是让 LLM 直接输出最终坐标。
4. 资产补齐使用 TRELLIS.2：它只负责生成单体 GLB，不负责自动布置完整场景。
5. 当前平台是最终执行层：所有自动搭建结果最终都要转换成当前项目已有的 `url + options.offset + options.scale + options.angle`。

## 4. 推荐落地架构

### 4.1 新增“语义搭建智能体”

建议在现有 AI 助手基础上扩展一个写入受控的新能力，命名可以是：

- 智能搭建
- 语义搭建
- AI 场景生成
- Scene Builder Agent

它不是普通聊天助手，而是有工具调用能力的场景搭建智能体。

建议工具分层：

1. 只读工具
   - 查询模型库：`model.search`
   - 查询模型元数据：`model.metadata`
   - 查询当前场景：`scene.current`
   - 查询业务对象和 IoT 设备：`iot.devices`、`business.objects`

2. 规划工具
   - 生成场景图：`scene.plan`
   - 生成布局：`layout.solve`
   - 校验碰撞：`layout.validate`
   - 估算模型缩放：`asset.fit`

3. 受控写工具
   - 前端预览：`scene.previewPlan`
   - 应用到当前场景：`scene.applyPlan`
   - 保存为草稿：`scene.saveDraft`
   - 缺失资产生成任务：`asset.generateJob`

第一版可以只做 `scene.plan -> scene.previewPlan -> 用户确认 -> scene.applyPlan`，先不自动保存数据库。

### 4.2 核心数据结构

建议定义一个中间协议 `ScenePlan`。它是整个功能的关键，比 prompt 本身更重要。

```ts
interface ScenePlan {
  sceneName: string
  intent: string
  units: 'platform'
  ground: {
    width: number
    height: number
    color?: string
    terrain?: 'flat' | 'field' | 'greenhouse_park'
  }
  objects: Array<{
    id: string
    label: string
    category: string
    assetKey?: string
    url?: string
    count: number
    position?: { x: number; y: number; z: number }
    rotationY?: number
    scale?: number
    layout?: 'single' | 'row' | 'column' | 'grid' | 'around' | 'along_path'
    area?: 'north' | 'south' | 'east' | 'west' | 'center'
    bindDeviceType?: string
  }>
  relations: Array<{
    subject: string
    predicate: 'near' | 'inside' | 'left_of' | 'right_of' | 'in_front_of' | 'behind' | 'around' | 'along'
    object: string
  }>
  missingAssets: Array<{
    label: string
    prompt: string
    fallbackCategory: string
  }>
  warnings: string[]
}
```

然后转换成当前项目已有格式：

```ts
{
  url: '/models/greenhouse.glb',
  options: {
    offset: { x: 300, y: 0, z: -200 },
    scale: 1,
    angle: 0
  }
}
```

这样可以直接调用现有 `Scene.loadModel(url, options)`。

## 5. 与当前平台的结合方式

当前项目已有能力：

- GLB 模型加载：前端 `Model.loadModel()` 使用 `GLTFLoader`
- 场景搭建：`Scene.loadModel(url, options)`
- 模板场景：`sceneTemplates` 和 `Scene.applyTemplate()`
- 场景保存：`Scene.saveScene()` -> 后端 `/scene/saveScene`
- AI 资产生成规划：TRELLIS.2 可生成单体 GLB 并入库
- AI 助手：已有 `/assistant/chat`、工具列表和上下文摘要

所以新增能力建议这样接：

### 5.1 后端新增接口

```http
POST /sceneApi/semantic/build/plan
```

输入：

```json
{
  "message": "搭一个智慧农业园区，左边三块玉米地，右边三个温室，中间放气象站和水塔，入口放摄像头",
  "sceneName": "智慧农业园区",
  "mode": "preview"
}
```

输出：

```json
{
  "planId": "plan-xxx",
  "scenePlan": {},
  "models": [
    {
      "url": "/models/greenhouse.glb",
      "options": {
        "offset": { "x": 300, "y": 0, "z": -200 },
        "scale": 1,
        "angle": 0
      }
    }
  ],
  "missingAssets": [],
  "warnings": []
}
```

可选接口：

```http
POST /sceneApi/semantic/build/apply
POST /sceneApi/semantic/build/save-draft
GET  /sceneApi/semantic/build/plans/:id
```

### 5.2 前端新增面板

在场景编辑页右侧或底部新增“AI 搭建”面板：

- 输入框：用户描述要搭建的场景
- 生成按钮：调用 `/semantic/build/plan`
- 计划预览：显示对象清单、缺失资产、布局警告
- 应用按钮：把返回的 `models` 循环调用 `scene.loadModel(url, options)`
- 保存按钮：沿用现有 `scene.saveScene()`

首版交互建议：

1. 用户输入需求。
2. 系统生成方案，但不立刻覆盖场景。
3. 右侧显示对象清单和预览结果。
4. 用户点“应用到场景”。
5. 用户可以手动拖拽微调。
6. 用户点现有保存功能。

### 5.3 模型库需要补语义元数据

语义搭建的效果，很大程度取决于模型库能否被检索。建议给模型表或资产表增加：

- `assetKey`：如 `greenhouse`, `corn`, `weather_station`
- `nameZh`：中文名
- `aliases`：别名，如“温室, 大棚, 玻璃房”
- `category`：建筑、作物、设备、传感器、道路、水体
- `defaultScale`
- `defaultFootprint`：占地宽深
- `placementRules`：可放置区域、是否贴地、是否可阵列
- `businessType`：可绑定的业务对象类型

没有这个语义索引，LLM 即使理解了“温室”，也不知道应该选哪个 GLB。

## 6. 第一版 MVP 怎么做

### 阶段 1：规则增强版，不训练模型

目标：一句话生成农业园区常见布局。

范围：

- 支持 10 到 20 类资产：温室、玉米、小麦、传感器、气象站、摄像头、水塔、仓库、管理楼、灌溉设备、道路等。
- 支持 5 类布局：单个、行列、网格、左右分区、沿道路。
- LLM 输出 JSON，程序做校验和坐标生成。
- 缺失资产先用模型库 fallback，不直接调用 TRELLIS.2。

验收示例：

> 搭一个智慧农业示范园区，左边 6 块农田，右边 3 个温室，中间一条路，路口放摄像头，中央放气象站。

平台应自动加载农田/作物、温室、道路、摄像头、气象站，并能保存。

### 阶段 2：接入 TRELLIS.2 生成缺失资产

当模型库没有某个资产时：

1. LLM 标记 `missingAssets`
2. 后端创建 TRELLIS.2 图片/模型生成任务
3. 生成 GLB 入个人资产库
4. 场景中先用占位模型或相近模型
5. 生成完成后可一键替换

示例：

> 在园区入口放一个卡通风格智慧农业欢迎牌。

如果模型库没有“欢迎牌”，则创建生成任务。

### 阶段 3：智能体闭环

增加多轮工具调用：

1. 读取当前场景已有对象。
2. 判断用户是在新建还是补全。
3. 检索模型库。
4. 生成布局。
5. 校验碰撞、越界、缺失资产。
6. 自动修正。
7. 给出可执行方案。
8. 用户确认后应用。

这时才是真正意义上的“场景搭建智能体”。

## 8. 关键风险

1. LLM 坐标不稳定  
   解决：LLM 只输出语义布局，坐标由规则布局器生成。

2. 模型库语义不足  
   解决：补资产标签、别名、默认尺寸、摆放规则。

3. 自动生成场景不符合真实业务  
   解决：沉淀农业场景模板和规则，例如温室成排、摄像头靠入口、传感器放在温室/地块内。

4. GLB 风格不统一  
   解决：MVP 优先用已有模型库；TRELLIS.2 生成资产走审核和缩放规范化。

5. 智能体误操作  
   解决：第一版只预览，不自动保存；写操作必须用户确认。

## 9. 可以向老师汇报的表述

本课题拟实现数字孪生平台的语义化智能自动搭建能力。用户通过自然语言描述场景需求，系统利用大语言模型解析场景语义，生成包含对象、空间关系、布局约束和业务绑定信息的结构化场景图；再结合平台已有 GLB 模型库、AI 资产生成模块和 Three.js 场景编辑器，将语义规划自动转换为可视化 3D 场景。该方法不是单纯聊天机器人，而是面向数字孪生场景构建的受控智能体，具备模型检索、布局规划、缺失资产生成、碰撞校验、场景预览和用户确认应用等工具调用能力。

技术路线采用“LLM 语义规划 + 规则/约束布局 + GLB 资产库 + Web 端渲染”的模块化方案。相比直接训练端到端 3D 生成模型，该方案工程可行性更高，更适合当前平台已有的模型加载、场景保存和 TRELLIS.2 资产生成链路。第一阶段实现自然语言生成标准农业园区布局，第二阶段接入 TRELLIS.2 生成缺失 GLB 资产，第三阶段形成可多轮交互、可读当前场景并自动补全的场景搭建智能体。

## 11. 基于 Eino DeepAgents 的详细实施方案

Eino DeepAgents 官方文档地址：

https://www.cloudwego.io/zh/docs/eino/core_modules/eino_adk/agent_implementation/deepagents/

根据官方文档，DeepAgents 是基于 ChatModelAgent 的开箱即用 Agent 方案，Eino 版本需大于等于 `v0.5.14`。它内置：

- `write_todos`：任务拆解与进度跟踪。
- `TaskTool`：主 Agent 调用子 Agent 的统一入口。
- `SubAgents`：拥有独立上下文窗口的子 Agent。
- `read_file/write_file/edit_file/ls/glob/grep`：文件系统工具。
- `execute`：Shell 执行工具。
- 默认 Prompt 与上下文管理能力。

但在数字孪生平台里，不能把 DeepAgents 的所有能力原样开放给用户。尤其是文件系统和 Shell 工具，生产环境必须关闭或放到后台开发环境使用。平台用户侧只暴露“模型检索、场景规划、布局求解、场景预览、资产生成任务”等白名单工具。

### 11.1 DeepAgents 在本系统里的定位

DeepAgents 不负责直接生成 3D 模型，也不直接操作 Three.js 画布。它应该作为后端“智能体总调度器”：

```text
用户输入自然语言
  -> Eino DeepAgents 主 Agent
  -> 调用模型库工具 model.search
  -> 调用场景规划工具 scene.plan
  -> 调用布局工具 layout.solve
  -> 调用校验工具 layout.validate
  -> 必要时调用 asset.generateJob 创建 TRELLIS.2 任务
  -> 返回 SceneBuildPlan 给前端
  -> 前端预览并由用户确认应用
```

主 Agent 适合做“判断与编排”，不要让它直接决定所有坐标。坐标应由确定性的布局器生成，这样结果稳定、可测试、可解释。

### 11.2 推荐 Agent 结构

建议采用一个主 Agent + 三个业务子 Agent：

| Agent | 职责 | 输入 | 输出 |
|---|---|---|---|
| `SceneBuilderAgent` 主 Agent | 接收用户请求，决定调用哪些工具和子 Agent，生成最终方案 | 用户自然语言、当前场景上下文 | `SceneBuildResponse` |
| `SemanticPlannerAgent` | 把自然语言转成对象、数量、关系、区域约束 | 用户描述、资产摘要 | `ScenePlan` |
| `AssetAgent` | 查询模型库，判断缺失资产，生成 fallback 或 TRELLIS.2 任务建议 | 对象清单、模型库元数据 | 资产匹配结果 |
| `LayoutAgent` | 将语义布局转为确定坐标，并校验越界/碰撞 | `ScenePlan`、资产 footprint、场地尺寸 | `models[]` 和 warnings |

MVP 可以先不真的拆成多个 Eino 子 Agent，而是在 Go 服务里用普通函数完成 `AssetAgent` 和 `LayoutAgent`。等第一版跑通后，再用 DeepAgents 的 `SubAgents` 和 `TaskTool` 做多 Agent 化。

### 11.3 工具白名单设计

第一版只开放这些工具：

| 工具名 | 类型 | 作用 | 是否允许写数据库 |
|---|---|---|---|
| `model.search` | 只读 | 按 `assetKey/中文名/别名/category` 检索模型 | 否 |
| `model.metadata` | 只读 | 返回模型默认缩放、占地、摆放规则 | 否 |
| `scene.current` | 只读 | 读取当前场景对象摘要，用于补全场景 | 否 |
| `scene.plan` | 规划 | 让 LLM 输出 `ScenePlan` | 否 |
| `layout.solve` | 规划 | 将语义区域和布局方式转成坐标 | 否 |
| `layout.validate` | 规划 | 检查越界、重叠、缺失模型、数量异常 | 否 |
| `asset.generateJob` | 受控写 | 对缺失资产创建 TRELLIS.2 生成任务 | 是，但需用户确认 |
| `scene.previewPlan` | 受控写 | 保存临时方案或直接返回给前端预览 | 可选 |
| `scene.saveDraft` | 受控写 | 将方案保存为草稿场景 | 是，必须用户确认 |

不建议开放：

- Shell `execute`
- 任意文件写入
- 任意 SQL 执行
- 任意 HTTP 请求
- 直接删除模型或场景
- 直接控制真实设备

DeepAgents 的文件系统、Shell 能力适合开发调试，不适合普通用户在线使用。

### 11.7 布局求解器设计

布局器不依赖大模型，建议用 Go 规则实现。输入 `ScenePlan`，输出当前平台可用的模型数组：

```go
type BuildModel struct {
    AssetKey string       `json:"assetKey"`
    Label    string       `json:"label"`
    URL      string       `json:"url"`
    Options  ModelOptions `json:"options"`
}

type ModelOptions struct {
    Offset Vector3 `json:"offset"`
    Scale  float64 `json:"scale"`
    Angle  int     `json:"angle"`
}

type Vector3 struct {
    X float64 `json:"x"`
    Y float64 `json:"y"`
    Z float64 `json:"z"`
}
```

支持的布局规则：

| 布局 | 用途 | 坐标生成方式 |
|---|---|---|
| `single` | 单个设备/建筑 | 放到指定区域中心 |
| `row` | 温室、摄像头、路灯 | 沿 X 或 Z 等距排列 |
| `column` | 温室纵向排列 | 固定 X，Z 方向等距 |
| `grid` | 农田、作物阵列 | 计算行列数，生成网格点 |
| `around` | 围绕中心放设备 | 圆形或矩形四周布置 |
| `along_path` | 沿道路布置 | 根据道路起止点插值 |

坐标区块建议：

```text
west   : x = -350 到 -100
center : x = -100 到 100
east   : x = 100 到 350
north  : z = -350 到 -100
south  : z = 100 到 350
```

这样用户说“左边/右边/中间”时，可以稳定转成坐标。

因此，“说出来就自动搭建”可以先做到 MVP 可演示、可保存、可迭代；要做到生产级，需要模型库、业务规则、资产质量和真实数据不断补齐。

### 11.11 推荐开发里程碑

#### 第 1 周：不接 Eino，先做规则版 MVP

- 新增 `ScenePlan` 类型。
- 新增模型语义索引 mock 数据。
- 新增规则布局器。
- 新增 `/semantic/build/plan`，先根据关键词和模板生成方案。
- 前端新增“AI 搭建”面板。
- 验收：输入标准农业园区描述，网页能自动放置模型。

#### 第 2 周：接 LLM 做语义解析

- 将关键词解析替换为 LLM 输出 `ScenePlan`。
- 增加 JSON schema 校验和失败重试。
- 增加模型库摘要注入 prompt。
- 验收：同义表达也能生成合理方案，例如“温室/大棚/玻璃房”都能匹配。

#### 第 3 周：接 Eino DeepAgents

- 引入 Eino 依赖。
- 封装 `SceneBuilderAgent`。
- 注册业务工具白名单。
- 禁用 Shell 和任意文件写入。
- 验收：复杂任务能拆解为“查模型、规划、布局、校验、返回方案”。

#### 第 4 周：接 TRELLIS.2 缺失资产闭环

- LLM 标记 `missingAssets`。
- 用户确认后创建资产生成任务。
- 生成完成后加入个人模型库。
- 前端支持一键替换占位模型。
- 验收：缺少“欢迎牌”等资产时，能进入生成任务而不是失败。

### 11.12 验收标准

MVP 验收用例：

| 输入 | 期望结果 |
|---|---|
| “搭一个智慧农业示范园区，左边 6 块农田，右边 3 个温室，中间一条路，中央放气象站。” | 自动加载农田/作物、温室、道路、气象站，布局左右分区清晰 |
| “创建标准温室场景，两个大棚，每个大棚里放传感器，旁边放灌溉设备。” | 生成 2 个温室、2 个传感器、1 套灌溉设备 |
| “在当前场景里补齐摄像头、水塔和气象站。” | 不清空当前场景，只新增对应设备 |
| “做一个综合农业园区，有管理楼、仓库、温室、农田和摄像头。” | 使用综合园区模板或生成相似布局 |
| “放一个智慧农业欢迎牌。” | 模型库没有时返回缺失资产提示或创建 TRELLIS.2 任务 |

必须满足：

- 生成结果能在网页 3D 场景中显示。
- 生成对象能被手动拖拽、缩放、旋转。
- 保存后重新打开场景不丢失。
- 没有模型时不崩溃，而是给出缺失资产列表。
- 写数据库动作必须由用户确认。
